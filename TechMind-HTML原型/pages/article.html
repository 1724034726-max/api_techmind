Redisson 分布式锁源码分析

#Redis#分布式锁#源码

背景介绍

在微服务架构中，分布式锁几乎是绕不开的话题。本文将从 Redisson 的 RLock 入手，顺着加锁、可重入、续期三条线把源码拆开看。

1. 加锁：为什么用 Lua？

Redis 单命令原子，但「判断 + 写入」需要组合语义。Redisson 把可重入计数与过期时间写进同一段 Lua，保证并发下不会撕裂。

if (redis.call('exists', KEYS[1]) == 0) then
  redis.call('hset', KEYS[1], ARGV[2], 1)
  redis.call('pexpire', KEYS[1], ARGV[1])
  return nil
end

可重入计数

同一线程再次加锁时，Hash 中的计数值加一；解锁则减一，减到 0 才真正删除 key。这与 JDK 的可重入锁语义一致。

2. WatchDog 续期

默认锁 30 秒过期。若业务未执行完，WatchDog 会按约 10 秒周期续期，避免长任务中途丢锁——也要注意进程崩溃后的锁释放策略。

若业务线程卡死，续期可能让锁长时间不释放，因此生产环境更推荐设置合理的 leaseTime，并在 finally 中主动 unlock。

3. 和生产相关的建议

明确锁粒度、失败重试退避，以及和「空值缓存 / 布隆过滤器」等方案组合，才能同时守住正确性与可用性。

监控持锁时长、超时告警，比单纯依赖默认参数更重要。

4. 与 Jedis 对比

Jedis 更轻，但续期、可重入、红锁等能力需要自行拼装；Redisson 开箱即用，代价是依赖更重、抽象层更多。选型时按团队运维成本与场景复杂度权衡即可。
